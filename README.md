# 矩阵流 · Alpha 0.01

一个面向抖音多账号运营的 Web 工作台，统一管理账号绑定、账号与作品数据、一键发布以及 DOU+ 投流。

当前阶段：Alpha 0.01 已实现可运行的基础 Web、后端、持久化和独立任务引擎。账号与投放采用明确标记的演示适配器，支持实际上传原创视频；尚未接入真实抖音账号、发布或广告支付。

开发任务与验收条件见 [TODO.md](./TODO.md)。

设计资料：[架构分析](docs/ARCHITECTURE.md)、[供应商能力矩阵](docs/PROVIDER_CAPABILITIES.md)、[场景验证报告](docs/SCENARIO_VALIDATION.md)。本轮 40 个离线模型场景通过，不能代替真实接口、数据库与端到端验收。

Alpha 当前实现、接口、测试和限制见 [Alpha 0.01 开发说明](docs/ALPHA_0.01.md)。后文 MVP 功能为完整产品目标，不表示已全部实现。

## 本地运行 Alpha 0.01

需要 Node.js 22.13 或以上：

```powershell
npm ci
npm run dev
```

访问 [http://127.0.0.1:3000](http://127.0.0.1:3000)，进入演示工作台。一个命令同时启动 Web 与 worker；数据默认保存在被 Git 忽略的 `.data/`。本版仅供本机体验，所有发布与 DOU+ 结果均为模拟，不会扣费。

```powershell
npm run typecheck
npm test
npm run build
npm run test:e2e
```

工程使用 TypeScript、Next.js 与独立 Node.js worker。SQLite 为零配置本地后端，设置 `DATABASE_URL` 可选择已实现但尚未在本机联调的 PostgreSQL 路径。生产构建的本地预览使用 `npm run build` 后运行 `npm run preview`。

## 1. 项目目标

用户在一个网页内完成以下流程：

1. 绑定多个自己拥有或获得授权的抖音账号。
2. 查看账号与作品数据，比较不同账号、素材的表现。
3. 上传原创视频，选择目标账号及发布参数，一键提交发布任务。
4. 为可投放的作品选择 DOU+ 目标、预算与时长，确认后批量提交投流任务。
5. 跟踪发布、审核、投流及花费结果，决定是否追加预算。

产品定位是提升多账号运营效率和素材测试效率，不承诺视频爆款、自然流量增长或成交结果。

## 2. 已确认需求

| 项目 | 当前约定 |
| --- | --- |
| 产品形态 | Web 管理后台 |
| 首期账号来源 | 自有抖音账号，后续支持用户绑定其拥有或获授权的账号 |
| 素材来源 | 用户原创视频 |
| 首期投流渠道 | DOU+ |
| 核心功能 | 多账号绑定、账号数据分析、一键发布、一键投流 |
| 商业化方向 | 按会员等级配置账号数量等权益，档位、数量和价格后续验证 |
| 后续扩展 | 商品挂载、团购挂载及相应投放渠道 |
| 当前接入条件 | 项目发起人暂无企业主体和营业执照，优先验证第三方服务商接入 |

“一键”指用户在确认账号、内容、参数和预算后，统一提交一批任务。每个账号和作品分别执行，可能出现部分成功；平台审核、实际发布时间和起投时间不保证同步。

## 3. MVP 范围

### 3.1 登录、工作空间与会员配额

- 建立产品自身的用户登录体系，产品登录与抖音账号授权分别管理。
- 每个工作空间维护独立的账号、素材、任务和数据。
- 预留套餐配置：可绑定账号数、素材存储量、任务配额、成员数等。
- 套餐额度由服务端统一校验，数量可配置，首期不写死价格和 VIP 档位。
- 套餐额度只约束本产品用量；抖音及服务商的接口额度和账号限制另行生效。
- 首期可采用内部试用方案；在线支付、订阅续费和复杂团队协作不作为首个闭环的前置条件。

### 3.2 抖音账号绑定与管理

- 用户通过接入方支持的授权页、二维码或客户端完成绑定。
- 展示昵称、头像、平台标识、分组、授权状态、已获能力与最近同步时间。
- 支持添加、解绑、重新授权、分组及筛选；实际操作是否能完全留在本 Web 内，以服务商接口为准。
- 若接入方仅提供账号读取接口，绑定和重新登录应引导用户到接入方完成，不展示虚假的站内绑定成功。
- 授权失效时停止依赖该授权的新任务，并提示处理已有未完成任务。
- 不将抖音密码、第三方密钥或授权令牌暴露给前端。

### 3.3 账号与作品数据分析

- 账号概览：在权限允许时展示粉丝量、作品数、点赞量等。
- 作品表现：在权限允许时展示播放、点赞、评论、分享等数据；完播、涨粉归因、转化等指标仅在来源明确支持时展示。
- 支持按时间、账号、账号分组、作品和素材筛选、比较。
- 展示数据来源、统计区间、更新时间和延迟说明。
- 区分账号累计值、区间变化和投放订单归因值，不混用不同口径。
- 缺失、无权限或暂未同步的数据显示“暂无数据”或具体原因，不填成 0。
- 付费与自然流量仅在接口能够区分时分别统计，不通过简单相减伪造自然流量。

### 3.4 素材库与一键发布

- 上传、预览和管理原创视频及封面，维护标题、话题和素材标签。
- 为不同目标账号配置各自的内容与发布参数。
- 首期支持立即发布；定时发布作为后续迭代，在授权和接口条件满足后开放。
- 提交前检查素材、账号授权、接口能力、参数、配额以及重复任务。
- 提交后生成一个批次及多个账号级任务，逐项显示执行结果。
- 保存外部任务 ID、作品 ID、作品链接和错误原因。
- 支持失败项单独处理；结果不确定时先核验原任务，不自动重新发布。
- 内容分发应遵守平台对同质化内容的限制，不以大量重复发布同一素材作为产品承诺。

### 3.5 DOU+ 一键投流

- 选择已发布、符合投放条件的作品，配置投放目标、人群、时长及预算。
- 参数选项、最低金额、可选目标与作品资格以接入方实时能力为准。
- 提交前展示账号、作品、每单预算、批次总预算及资金来源，用户明确确认后执行。
- 设置单单、单批、每日确认额度与跨日在途预算上限；并发提交时也不能突破产品侧授权额度。每日确认额度按确认日归集，不等于平台每日实际消耗上限，外部入口投放不受本系统直接约束。
- 每个作品建立独立投流任务，记录外部订单、支付状态、审核状态、投放状态和实际消耗。
- 创建订单、付款和开始投放分别记录；“订单已创建”不能显示成“正在投放”。
- 支持查询、停止及追加预算的程度，以获批接口为准。
- 首期追加预算由用户发起；按效果自动追加作为后续功能，须有单独配置的规则、额度和停止条件。
- DOU+ 费用由用户在官方或接入方支持的投放账户支付；首期不自建充值钱包、不代收投放资金。
- 软件会员费与实际广告消耗分别记录。

## 5. 第三方接入策略

业务通过服务端的接入适配层调用第三方平台。账号、发布、数据、投流可使用不同服务商，但跨服务商的账号和作品标识必须建立可靠映射。

拟支持的能力分类：

- 账号：授权引导、列表、状态、解绑及重新授权。
- 内容：素材上传、参数查询、发布、任务状态及作品查询。
- 数据：账号指标、作品指标、历史区间与同步状态。
- 投流：投放资格、参数、余额、创建订单、付款、订单查询、停止及报表。
- 通知：授权变更、发布结果、审核结果和投流状态回调。

每项能力分别标记为“未验证、可用、不支持、需人工完成”。前端按真实能力开放操作，不因某个平台宣传支持抖音就默认其开放全部接口。

这些是候选，不代表已签约、已获得抖音官方合作认证或已完成接口测试。公开资料核对日期：2026-10-27。价格与合作条件待供应商确认。

第三方提供 API 只说明其对外调用方式；底层是否为官方接口、客户端或其他执行机制，需要单独核实。

### 接入放行条件

正式接入前必须得到以下结果：

1. 接入方接受当前申请主体，并允许预期的商业使用方式。
2. 用户账号的授权、失效、解除及数据处理方式明确。
3. 用少量真实自有账号跑通绑定、发布、结果回收和可用数据同步。
4. DOU+ 实际跑通下单、付款或人工付款衔接、审核和结果查询，明确哪些环节可自动化。
5. 明确失败、超时、重复提交的处理方式，以及费用、限流和支持渠道。

可以在验证期间开发模拟页面和业务流程，但模拟数据必须显著标记。只完成模拟流程不能作为真实发布或真实投放功能验收。

## 6. 系统设计原则

- 架构采用模块化单体业务后端与独立任务进程，结合 Web、PostgreSQL、私有对象存储和服务商适配层。首期使用数据库持久任务，同事务提交业务与任务；推荐 TypeScript、Next.js Web/API 和独立 Node.js worker，具体版本和部署产品待工程初始化时锁定。
- 发布和投流采用异步任务；用户提交后可离开页面，状态由后台继续跟踪。
- 内部保存稳定的账号、作品、素材及任务 ID，同时保存带服务商命名空间的外部 ID，不能假定不同应用的账号 ID 通用。
- 采用“发布批次 → 账号级任务”和“投流批次 → 作品级订单”的结构，支持部分成功。
- 对写操作实施幂等控制；超时或结果不明确时进入核验状态，禁止盲目重试发布或付款。
- 预算统一以整数分保存，时间统一保存标准时间并按用户时区展示。
- 回调验证来源与签名，处理重复及乱序事件；回调缺失时采用有频控的查询补偿。
- 统计同步保存来源与时间，支持延迟数据更新和合理范围内的补采。
- 所有数据读取与操作均校验工作空间归属；授权令牌仅在服务端加密保存，日志脱敏。

建议的核心实体：用户、工作空间、套餐及配额、平台账号、账号授权、素材、作品、发布批次、发布任务、投放批次、投放订单、预算占用、指标快照、回调事件、审计日志。

## 7. 后续扩展

- 会员付费、订阅和更完整的团队权限。
- 定时发布、内容审批和素材版本管理。
- 在数据及控制接口允许时，按规则追加投放或停止后续投放。
- 商品挂载与团购挂载：分别确认账号资格、商品或门店关联及接口权限。
- 根据挂载类型扩展适用投放渠道，不能默认所有挂商品视频均可投 DOU+。
- “发布时挂载”与“已发布作品补挂”分别验证，不能默认支持补挂。

## 8. 当前不承诺的能力

- 在没有可用授权或接口时，宣称已实现真实的一键发布或投流。
- 账号注册、购买、密码托管、绕过验证码或平台授权限制。
- 不受限制的同质化视频群发、无限自动续投或保证爆款。
- 通过模拟订单、估算数据或不明确口径展示实际广告效果。

## 10. 离线场景验证

在项目根目录使用 Python 3.10 或以上运行：

```powershell
python -m unittest discover -s validation -p 'test_*.py' -v
```

脚本只使用标准库和内存模型，不连接网络、不操作真实账号、不产生投流费用。它用于检查业务不变量；生产数据库并发、签名验证、进程恢复和真实供应商行为仍需后续集成验证。
