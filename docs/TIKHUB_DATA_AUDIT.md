# TikHub 对矩阵流数据需求的专项核对

日期：2026-10-27（Asia/Hong_Kong）。主体结论基于公开文档与 OpenAPI；后续账户鉴权、价格元数据及单视频公开接口检查见第7、8节。未使用抖音账号 Cookie，未调用私有创作者数据接口。

## 1. 结论与覆盖范围

TikHub 已有作品深度指标及若干趋势接口，可以进入“作品级分析”的候选验证阶段；公开资料尚不足以确认其完整提供矩阵流当前的账号每日 9 项作品指标 + 5 项粉丝指标，并覆盖昨天、近7天、近30天。主要缺口是账号日报口径、粉丝吸粉/脱粉/回访、普通账号的历史数据范围，以及 Cookie 登录与会员商业许可。

本次读取[完整目录](https://docs.tikhub.io/)，下载并检索[公开 OpenAPI V5.3.2](https://api.tikhub.io/openapi.json)。规范包含1050项操作；路径含 `/douyin/` 的321项中，319项属于正式抖音目录，2项是固定数据 Demo。正式目录覆盖 Web 55、App V3 38、Creator 17、Creator V2 14、Index 51、Search 23、Billboard 31、Xingtu 23、Xingtu V2 50、DouPlus 17 项。已对全部14个 Creator V2 逐项阅读，并检查其余抖音目录中账号、粉丝、日趋势、作品指标候选的参数与说明；其他平台仅作目录识别，不将 TikTok 指标当成抖音能力。也核对了入门、业务限制、FAQ、服务及隐私条款。

这比前次初查补充了“作品四项深度观看指标有文档支持”和“星图每日粉丝趋势有候选接口”，但仍未得到完整账号日报可替换的证据。

## 2. 当前14项指标对照

判定中的“作品支持”只代表文档描述作品级字段；“日报待验”代表尚无真实逐日响应与官方 Excel 对照，不能标为已满足。

| 指标 | 可用候选 | 对当前账号每日报表的判断 |
| --- | --- | --- |
| 投稿量 | 作品列表按发布时间筛选；账号诊断近7天投稿数 | 部分支持。删除、私密、体裁和列表完整性会影响按列表计数 |
| 总播放量 | 投稿表现 `metric_type=1`、作品指标 | 日期范围候选；需核实期间观看行为是否覆盖此前发布的全部作品 |
| 总点赞量 | 投稿表现 `metric_type=2`、作品指标 | 日报待验；不能把周期内新发作品的当前累计值当作周期内全账号新增 |
| 总分享量 | 投稿表现 `metric_type=4`、作品指标 | 日报待验，同上 |
| 总评论量 | 投稿表现 `metric_type=3`、作品指标 | 日报待验，同上 |
| 5秒完播率 | 投稿作品列表列出对应指标 | 作品支持；未确认账号每日字段及加权分母 |
| 2秒跳出率 | 投稿作品列表列出对应指标 | 作品支持；未确认账号每日字段及加权分母 |
| 封面点击率 | 投稿作品列表列出对应指标 | 作品支持；未确认账号每日曝光/点击分母 |
| 平均播放时长 | 投稿作品列表、星图作品指标 | 作品支持；未确认账号每日总时长及播放分母 |
| 总粉丝量 | Web用户资料；星图每日粉丝趋势 | 当前值/历史趋势候选；需确认 `daily` 含义、普通账号覆盖及实际日期完整性 |
| 粉丝净增 | 账号诊断 `NewFans`；星图趋势 `delta` | 诊断仅固定近7天汇总；星图字段精确定义待验，无法直接确认完整三周期日报 |
| 吸粉量 | 作品列表的作品带来关注数、直播新增关注 | 这些是归因范围，未确认账号每日全部吸粉量 |
| 脱粉量 | 未检索到明确对应的账号每日接口说明 | 未确认；粉丝总数相减只能得到净变化，不能拆出吸粉与脱粉 |
| 回访粉丝量 | 未检索到明确对应的账号每日接口说明 | 未确认；粉丝观看占比和粉丝画像都不能替代回访人数 |

主要证据：[作品列表](https://docs.tikhub.io/359719871e0)、[投稿表现](https://docs.tikhub.io/359719870e0)、[账号诊断](https://docs.tikhub.io/359719874e0)、[每日粉丝趋势](https://docs.tikhub.io/489299445e0)。文档中出现字段不等于当前目标账号能稳定返回该字段。

## 4. 其余接口能否补齐

- [星图每日粉丝趋势](https://docs.tikhub.io/489299445e0)提供日期参数，描述包含 `daily/delta`，适合做历史粉丝曲线的候选。文档缺少字段精确定义和普通账号全覆盖保证，不能推定等同官方粉丝Excel。
- [Billboard账号粉丝趋势](https://docs.tikhub.io/252393847e0)标题为粉丝趋势，但参数 `option` 的说明是赞/作品/评/分享；[账号作品分析](https://docs.tikhub.io/252393848e0)标题为上周，描述提到 `day`，OpenAPI请求参数却没有该字段。需向供应商核实，不能自行添加隐藏参数或承诺30天。
- Index 的发布/互动/消费日趋势按内容垂类 `tag_id` 查询，属于行业内容数据，不能用来填自有账号日报。粉丝画像也不能替代粉丝数量及增减。
- Web/App V3 是账号资料、作品及当前统计的候选，单次累计数无法补回历史日增量。[星图播放量](https://docs.tikhub.io/493289600e0)还明确区分含投流总量与App V3所描述的不含投流量；两者不能无标识混合。
- Creator V1主要为活动、课程、素材和热点内容。Search/Index/Billboard可扩展选题和对标；DouPlus的投放报表属于投放范围，不能代替账号整体报表。

## 5. 网页集成、授权与文档不足

云端后端可以调用 TikHub API，因此从执行位置看，可以省去本机常驻助手。深度接口同时要求 TikHub API Key 和创作者 Cookie；[FAQ](https://tikhub.io/zh/faq)没有提供替矩阵流完成抖音官方OAuth、自动刷新用户登录态的能力。用户仅填写账号ID并不能读取其私有分析。当前仓库不向第三方发送 Cookie，这次调研没有改变此约定。

[标准服务条款](https://docs.tikhub.io/9453286m0)默认许可限定内部业务用途，第三方再分发等需书面许可，并未保证其访问方法获得来源平台授权。付费多用户网页产品需就具体集成方式取得许可，API Key和余额不自动完成该步骤。

技术验收还受以下文档缺口影响：

1. OpenAPI的200响应主要使用通用 `ResponseModel`，`data` 未定义具体结构；目前不能只靠生成SDK固定日报字段映射。
2. 作品导出描述同时出现异步任务和直接文件流，而OpenAPI 200又是通用JSON；真实响应及轮询方式需确认。
3. 日期筛选可能指作品发布时间，也可能指统计发生日，必须逐接口核实；旧作品在近期产生的流量是关键对照样本。
4. Cookie过期、缺失字段、样本阈值、0值、负值、账号ID映射和授权前历史都需目标账号响应取证。
5. 收费按接口和调用量，分页与多个指标增加请求数；未完成字段映射前不估固定账号日成本。调试缓存和请求追踪中的Cookie脱敏/保留方式也应向供应商确认。

## 6. 建议的验证门槛

可以先把 TikHub定位为作品级数据源候选。完整替换现有日报前，要求供应商提供：账号每日9项作品指标和5项粉丝指标的明确端点、字段路径、三周期样例；星图普通账号覆盖说明；Cookie接入与更新流程；会员多用户产品许可。随后在用户明确允许使用密钥和发送特定账号Cookie后，选一个自有账号，与官方Excel逐日对照，记录缺失和差异。

文档审查结论：作品级分析具备较强可行性；现有账号/粉丝全量日报尚未证实完整满足；仅网页官方授权和商业上线条件尚未满足。本次没有实现或验证TikHub适配器。

## 9. 单视频近30天历史的后续排查

对用户指定视频调用Billboard `fetch_hot_item_trends_list`（`option=7`、`date_window=2`）及一次错误诊断重试，均返回HTTP 400和通用重试提示，响应明确说明失败请求不扣费。未取得历史记录，错误未明确说明缺失原因，不能推断为该视频绝无历史或接口完全不支持。

星图 `get_item_report_trend` 的公开元数据返回基础价格0.003美元、不接受免费额度；初查时账户无付费余额，因此当时未调用。用户登录市场后已完成一次真实查询，结果见第11节。其文档请求只有 `item_id`，没有开始/结束日期及固定30天范围保证。Creator V2投稿表现有日期范围但无 `item_id`，也不能据此证明可取得某一视频完整30天日报。

已有累计快照不能倒推出过去30日。历史应以创作者后台实际提供的日期报表或经实测完整的趋势接口为准；从现在持续保存同源累计快照只能形成之后的净变化记录，缺失历史保留缺失。

## 11. 登录市场后的3次真实查询

2026-10-27，使用用户先前提供的TikHub密钥及指定视频ID，分别调用上述两个Index接口和 `POST /api/v1/douyin/xingtu_v2/get_item_report_trend` 各一次，均为HTTP 200、TikHub code 200、底层状态码0。三个响应均声明成功计费，按当时市场标价合计0.005美元；未另查账单核对实际结算。未发送抖音Cookie，未执行发布或投流。真实响应仅保留在被Git忽略的 `.data/research/`。

- Index两个请求均以Query传入 `item_id`、`start_date=20260927`、`end_date=20261026`。返回日期覆盖这30天，但指数及互动序列全为0，且没有播放次数字段。不能将指数的0解释成真实播放为0，也不能从本次全0响应判断是无收录还是没有变化。
- 星图趋势请求体只有 `{"item_id":"<视频ID>"}`。真实响应含 `data.date_values.vv_list`、`valid_vv_list`、点赞、评论、分享、收藏、完播率、热度和互动序列。各记录形如 `{"value":"<数值>","visit_date":<YYYYMMDD>}`；数值为字符串，部分互动记录可为负数，应原样保留。比率字段单位没有在此响应中说明，不自行换算或累计。
- 该样本 `vv_list` 有连续、无重复的30个自然日，从视频发布当天起；返回区间不是本次检查时的最近30天。已检查日期连续性及播放值合计；具体日期、计数及逐日明细留在本地忽略目录，不写入可提交项目文档。单个样本不能证明该接口对所有视频都固定返回发布后30天，也不能证明其支持自选日期或后续分页。
- `vv_list` 可作为单视频历史播放趋势候选；`valid_vv_list` 是另一个独立字段，精确定义及与官方后台的对应关系尚待核实。没有将星图趋势与App V3累计数混成同一口径，也没有据此解除此前分享量跨接口差异的待核状态。

本轮修正结论：**确实取得了指定视频一段30天的历史逐日播放数据；仍未证实可按任意起止日期查询该视频的播放次数。** 对账号投稿表现，文档明确提供日期范围与播放指标，但需用户另行授权向TikHub发送创作者Cookie后才能实测，且没有单视频ID筛选。Creator V2、完整账号/粉丝日报、商业使用许可及产品适配器仍未验收。

## 13. 用户资料查询的有限实测

用户随后提供一个数字标识，要求按UID查看实际返回字段。`web/fetch_user_profile_by_uid` 与 `web/handler_user_profile_v3` 均返回HTTP 200、TikHub外层code 200，但底层 `data.status_code=20001`，错误对象提示“该用户不存在”，没有用户资料。将同一数字按抖音号交叉查询，`web/handler_user_profile_v2` 返回HTTP 400；`creator/fetch_user_search` 返回HTTP/外层200、底层状态0，但没有用户列表或可核实的精确匹配。不能据此认定账号客观上不存在，也不能补造昵称、粉丝数等字段；需由用户主页链接确认标识和接口覆盖后继续。

这4次只读请求没有发送抖音Cookie，真实标识与响应仅在忽略目录。用户资料/作品列表尚未实现产品适配；将来适配必须同时检查底层状态、数据结构及返回账号身份，不能只凭HTTP或TikHub外层200宣告查询成功。

用户随后提供另一账号的抖音号截图，按 `web/handler_user_profile_v2?unique_id=...` 查询成功：HTTP/外层code 200、底层status_code 0，`data.user_info` 返回26个顶层字段（先前人工计数误写为27，后以Object.keys核实更正），昵称与抖音号和截图一致。这证实该端点对这一样本可用，先前数字标识失败不能推定整个端点不可用。包含头像、签名、关注数、作品数、喜欢数、获赞、认证及 `sec_uid` 等；没有返回内部 `uid` 或标准 `follower_count`。`short_id` 返回占位值，不能当作已核实UID；另有 `mplatform_followers_count`，精确定义待核实，不能直接替代官方粉丝日报。真实账号标识与字段值仅保存于忽略目录。尚未查询该账号作品列表，也未将用户查询接入产品。

用户表示关闭“可被他人搜索到”后，2026-10-27再调用同一抖音号定向查询端点一次，仍返回HTTP/外层200、底层0；账号抖音号与sec_uid匹配之前响应，26个字段的集合及已核对计数一致。未读取或更改用户隐私设置，未测试搜索结果列表，也未验证设置生效延迟或供应商缓存，因此不能据此宣称搜索开关无效或所有账号关闭搜索后均可查询。前后实际响应分别留在忽略目录。

用户随后明确：前面失败的数字是抖音号，而非内部UID。因此，之前UID端点的“用户不存在”不适用于判断这个抖音账号的存在性。按正确 `unique_id` 参数再次调用 `web/handler_user_profile_v2`，并通过 `search/fetch_user_search` 按同一数字搜索，均返回HTTP 400通用失败提示；两个响应均注明本次不收费，没有提供可归因于隐私开关或账号不存在的具体错误。没有取得精确匹配及sec_uid，因此未继续调用sec_uid资料端点。后续需主页分享链接解析标识，不能反复把抖音号作为UID重试。

用户补充主页短链后，使用不带Cookie的HTTPS请求，校验跳转域名并从抖音主页重定向路径提取sec_user_id。随后 `app/v3/handler_user_profile?sec_user_id=...` 返回HTTP/外层200、底层0，用户资料含136个顶层字段；返回unique_id与用户此前提供的抖音号完全一致。取得内部UID后，再用 `web/fetch_user_profile_by_uid?uid=<真实UID>` 查询，也返回底层0，并以 `data.data.id_str`、`sec_uid`、`display_id` 与前一个响应交叉核对一致。该UID端点的数据结构是 `data.data`（包含follow_info等），不能硬编码成App接口的 `data.user`；UID优先使用id_str，避免数值精度问题。

当前已证实该账号可以读取公开资料，之前UID查询的20001由传入抖音号而非真实UID解释；抖音号直查400的具体原因仍未确认，不能归因为隐私设置或宣称已修复服务商端点。产品后续可采用主页链接解析→sec_uid查询→保存真实标识的路径；不能只凭纯数字猜测UID或抖音号类型。本轮没有开发账号资料页面/适配器，没有查询作品列表或修改隐私设置。真实标识、指标及响应仅保存在忽略目录。

进一步验证“仅输入数字抖音号”的路径成功：向 `GET /api/v1/douyin/web/fetch_user_profile_by_short_id` 只传 `short_id=<用户提供的数字抖音号>`（未传已知UID、sec_uid或主页链接），HTTP/外层200、底层0，`data.data.user` 返回昵称、头像、`id_str`、`sec_uid` 等基本资料。再动态读取这次响应中的sec_uid调用App V3资料接口，取得136个字段，返回unique_id与原始输入一致，UID与第一步id_str一致。完整两步链路已真实验证，无需用户另行提供主页链接，也没有使用旧身份映射。

此前排查漏测了这一Short ID专用端点，现已补测。此结果适用于该样本，不能直接扩展为任意纯数字抖音号都等于Short ID；将来产品需核对返回抖音号/UID/sec_uid，失败时提供主页链接入口，不能静默绑定相似账号。抖音号直查v2的400原因仍未解决；本轮仅研究及实测接口，没有开发用户查询功能。

用户随后确认添加账号流程，已在 `/accounts` 实现抖音号解析与完整资料获取、身份核对、预览及确认保存。数字抖音号使用Short ID优先、unique_id为一次备选，字母抖音号走unique_id；严格匹配返回身份，失败不绑定。对已指定数字抖音号通过真实应用路径联调，仅测试隔离数据库；没有扩大为所有抖音号覆盖保证。最新工程与验收见项目记忆第18节，前文“尚未开发用户查询”均为当时调研状态。

## 14. 账号获取作品URL的单页实测

用户询问能否通过账号信息获取作品URL后，使用此前已核实账号的sec_uid，调用一次 `GET /api/v1/douyin/app/v3/fetch_user_post_videos`，显式传入max_cursor=0、count=20、sort_type=0、channel=normal。HTTP/外层200、底层状态0，返回4条作品，has_more=0；逐条核对作者UID与目标账号一致。响应含aweme_id及作品分享URL，也出现视频/图文不同类型，不能一概按视频处理；列表与URL数据仅在忽略目录，不写入项目文档。
